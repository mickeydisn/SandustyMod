Overview

In-game configurator to define and register elements, structures, items, recipes, processing, contact reactions, and more — all via JSON stored in game storage.

No item required. The panel is a movable, minimizable overlay (minimized by default). Open it from the chip that appears after the mod loads.
Style note. This documentation mirrors the in-game panel chrome (dark blue-grey panels, gold accent on active nav, system UI colours from the mod). Titles use a pixel font (Press Start 2P) for a Sandustry-like feel; body text stays readable with IBM Plex.

What this mod does

You author game content entirely from a panel inside Sandustry. Every definition is saved as JSON in the mod’s storage. On load (and after edits) the mod registers those definitions with the sandkit API so they become real elements, buildings, tools, reactions, and behaviours in the world.

Getting started

Enable the mod, open the panel, create your first element.

1. Enable the mod

In the game’s mod settings, turn Enabled on. The setting also controls whether the panel starts minimized.

2. Open the panel

A small chip appears (usually bottom-right). Click it to expand the overlay. The panel is near-fullscreen while open; the chip is what you drag when minimized.

3. Create an entry

  1. Pick a group and tab (e.g. Content → Elements).
  2. Press + New.
  3. Fill the form. Required fields are marked.
  4. Save. The entry is written to storage and registered with the engine.

4. IDs

Every object needs a unique string id. Prefer a short prefix for your own content, e.g. mdmy:dust or md-my-hown-mod:dust. Both prefixes are treated as “this mod” by the panel filters.

Changing an id after the object is used elsewhere (recipes, contacts, unlocks…) breaks those references. Prefer renaming the display name instead.

Config shape

The entire mod state is one JSON document stored under the key config.

{
  "version": 1,
  "elements": [ /* ElementConfig */ ],
  "structures": [ /* StructureConfig */ ],
  "items": [ /* ItemConfig */ ],
  "terrains": [ /* TerrainConfig */ ],
  "recipes": [ /* RecipeConfig */ ],
  "processing": [ /* ProcessingConfig */ ],
  "contacts": [ /* ContactReactionConfig */ ],
  "interactions": [ /* InteractionConfig */ ],
  "modifiers": [ /* ModifierConfig */ ],
  "techs": [ /* TechConfig */ ],
  "unlockNodes": [ /* UnlockNodeConfig */ ],
  "upgradeCategories": [ /* UpgradeCategoryConfig */ ],
  "upgrades": [ /* UpgradeConfig */ ],
  "projectiles": [ /* ProjectileConfig */ ],
  "excavationProfiles": [ /* ExcavationProfileConfig */ ],
  "structureBehaviors": [ /* StructureBehaviorConfig */ ],
  "placementConfigs": [ /* PlacementConfigConfig */ ],
  "signals": [ /* SignalConfig */ ],
  "triggers": [ /* TriggerConfig */ ],
  "sprites": [ /* SpriteConfig */ ],
  "inputBindings": [ /* InputBindingConfig */ ],
  "energyTypes": [ /* EnergyTypeConfig */ ],
  "energyNetworks": [ /* EnergyNetworkConfig */ ],
  "buffers": [ /* BufferEntryConfig */ ],
  "processes": [ /* CustomProcessConfig */ ]
}

Empty arrays are fine. Missing keys are filled with [] on load. Legacy actions arrays on signals / triggers / processing / etc. are automatically migrated into derived processes.

The panel

How the UI is organised and how lists work.

Navigation

Top chips select a group. Under the group, tabs select a category. Most categories show a list of entries with + New. Opening an entry (or creating one) opens the Edit form.

Attached lists

Some lists live under another object rather than as their own tab:

  • Tooltips → under Elements
  • Placement fields, Behaviours, Signals → under Structures
  • Excavation profiles, Projectiles → under Items
  • Unlock nodes → under Tech nodes
  • Upgrade categories / Upgrade actions → under Upgrades

Fixed catalogues

Excavation options and Projectile options are read-only lists written in code. They have no Edit form and no + New — they are reference catalogues for the presets the compiler understands.

Filters

Every list has a search box, owner chips (This mod / Game), and a toggle for hidden objects.

Important: flammable: true is silently ignored by the engine. The fire pass requires an object. An empty object {} means "burns and leaves nothing". Sub-keys control residue and fire lifetime.
Sub-fieldTypeNotes

Buffers

Shared slots every process in this mod can read and write.

A buffer slot is not one machine’s memory — it is a single value every process agrees on. Structure data bags are private; buffers are the cross-structure counter / flag store.

Fields

FieldNotes
pathSlot key (string)
typeValue type (number, boolean, …)
valueInitial value
min / maxRequired for numbers — counters are always clamped

From a process use the Remember actions: bufferRead, bufferWrite, bufferIncrement. A path that no slot declares is a no-op on write and the type’s zero on read.

Processors

Timed behaviour attached to a structure type. Runs a process on the processing call site.

Each entry names a structure type and a processId (or legacy actions array). The engine calls the compiled process with structure coordinates and a commit function for deferred cell mutations.

Relations

Research nodes: cost, branch, what they unlock.

Tech nodes form the research tree. They can unlock structures (via unlock nodes), items, or other content. Costs are usually gold / fluxite / energy currencies.

Unlock nodes

What each structure is gated behind: free from the start, or behind research.

Every structure should name an unlock node. The built-in default node means “unlocked from the start”. Custom nodes are linked to tech nodes so research grants the structures.

Upgrades are organised into categories. Each upgrade level can run a process (upgrade scope) when applied. Upgrade actions are the subset of atomic actions that only make sense at the upgrade call site.

Custom processes

Named, reusable handlers built from atomic actions. Edit once — every call site updates.

Why processes exist

Previously every signal, trigger, and processor stored its own actions: [{ key, options }] array. There was no way to name that behaviour or reuse it. A custom process is a first-class object with:

  • an id and optional name / doc
  • a scope (call site) that seeds the context
  • an ordered list of steps { key, options?, as? }

Fields

FieldNotes
idProcess id
nameDisplay name
scopesignal · trigger · processing · itemAction · upgrade · behavior · modifier
stepsArray of action steps
docAuthor notes
derivedTrue if auto-migrated from a legacy actions array

Scopes & context seeds

Each scope seeds a read-only context from what the engine actually passes at that call site:

ScopeContext seeds (read-only)
processing structure.x, structure.y, structure.type, structure.data, context.getResolvedTypeAtCell, context.isCellEmptyAtCell, context.commit
signal structure.x, structure.y, structure.type, structure.data
trigger tick (callback takes no other arguments)
itemAction state.x, state.y, action.type
modifier args, ctx
upgrade item.type
behavior key

Author variables (bound with as:) live in a separate writable namespace. Seeds cannot be overwritten.

Call sites that reference a process

Signals → processId Triggers → processId Processing → processId Items (itemAction) → processId Upgrades → processId Modifiers → processId
A definition stores a reference (processId), never a copy of the steps. Editing the process updates every use. The panel shows used ×N so the blast radius is visible.

IDs & prefixes

How the mod attributes objects to itself vs the game.

Object ids that start with either of these prefixes are treated as belonging to this mod:

  • md-my-hown-mod — the package / mod id
  • mdmy — the short author prefix used in config examples

The panel’s “This mod” filter and the origin tags on list rows read that list. Prefer a consistent short prefix for everything you create.

Never reuse a vanilla or another mod’s id. Collisions cause silent overwrites or registration failures depending on the engine path.

Storage keys

The mod persists two keys under its storage bag:

  • config — the full ModConfig JSON
  • panel — position, size, minimized state of the overlay
